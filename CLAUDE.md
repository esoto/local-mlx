## What this project is

**LocalMLX** — a native macOS SwiftUI chat app for [`mlx_lm.server`](https://github.com/ml-explore/mlx-lm), Apple's MLX LLM server. OpenAI-compatible backend, Ollama-style frontend, runs entirely locally on Apple Silicon.

- GitHub: `esoto/local-mlx`
- Active branch: `claude/macos-llm-chat-app-RF5RK`
- macOS 14+ / Swift 5.10 / SwiftUI / SwiftData
- Xcode project is generated by XcodeGen from `project.yml`

## **Critical context — read this first**

**None of this code has ever been compiled.** It was all written on a Linux host with no access to Xcode or `xcodebuild`. The TDD suite is carefully paired with the implementation, but the first `xcodebuild` on a real Mac is the first time anyone finds out whether it actually works.

**Your first job in a new session is to try to build and test it**, not to add features. See "How to continue" below.

## How to continue

**Step 1: Build and test, fix whatever breaks.**

```sh
# from repo root on a Mac
brew install xcodegen
swift tools/generate-icon.swift      # optional — renders app icon PNGs
xcodegen generate
xcodebuild test \
  -project LocalMLX.xcodeproj \
  -scheme LocalMLX \
  -destination 'platform=macOS'
```

When errors come up, they are my bug, not the user's. Fix the implementation to match the test expectations, not the other way around, unless the test is obviously wrong. The tests were designed before or alongside the impl and encode the intended behavior.

**Step 2: Run it against a real mlx-lm server.**

```sh
python3 -m venv .venv && source .venv/bin/activate
pip install mlx-lm
mlx_lm.server --model mlx-community/Llama-3.2-3B-Instruct-4bit --port 8080
```

Then in the app: new chat, pick model, send "Say hi", confirm tokens stream and the tok/s footer appears. Test Stop mid-stream. Test regenerate, edit, fork, delete, export. Test "Open in New Window" from the sidebar context menu.

**Step 3: Only after both of the above pass, add new features.** Pick from "Backlog" below.

## Architecture notes you need to know

### Streaming pipeline
`LiveMLXClient.streamChat` returns `AsyncThrowingStream<StreamEvent, Error>`. `StreamEvent` is `.delta(String) | .usage(UsageStats)`. The consumer (`ChatViewModel`) accumulates deltas into `assistantMsg.content` (debounced at 33 ms) and captures usage into a local. At stream end, it writes `promptTokens`, `completionTokens`, `tokensPerSecond`, and — on error — `interruptionReason` onto the assistant `Message`.

### Cancellation chain
1. `ChatViewModel.stop()` → `streamingTask.cancel()`
2. The streaming consumer's `for try await` observes cancellation
3. `AsyncThrowingStream.onTermination` fires → cancels the producer Task inside `MLXClient.streamChat`
4. The producer's `Task.checkCancellation()` or `bytes.lines` iteration throws
5. `continuation.finish(throwing: MLXClientError.canceled)`
6. Caught by `catch MLXClientError.canceled` in the consumer — logs, skips banner (Stop is not an error), defer runs `isStreaming = false`, saves

### Clock injection
`ChatViewModel.init(now: () -> Date, wallClock: () -> Date)`. `now` is used for `createdAt`, `updatedAt`, and auto-title logic — frozen in tests for determinism. `wallClock` is used for tok/s measurement — stays real even in tests so elapsed time is non-zero.

### Shared state
- `AppSettings` — `@StateObject` in App, `@EnvironmentObject` in views. Not `@MainActor` so the MLXClient closure can read `makeBaseURL()` from any Task.
- `ModelsViewModel` — `@MainActor private static let sharedModelsVM` on `LocalMLXApp`, passed via `.environment(modelsVM)` → `@Environment(ModelsViewModel.self)`. One instance, polled once, read by every window.
- `MLXClientEnvironmentKey.LiveHolder` — boxed `any MLXClientProtocol` for environment injection.

### Message ordering
`Conversation.sortedMessages` sorts by `createdAt`. Under the frozen test clock both user and assistant messages would have the same timestamp, so `ChatViewModel.generate` offsets the assistant placeholder by 1 ms to force a deterministic order. Don't remove that offset — tests depend on it.

### Auto-title
Only fires when `conversation.title == "New Chat"`. After the first send writes a title (≤ 40 chars, truncated with "…"), subsequent sends and renames leave it alone. Branching sets `"(fork)"` suffix with incrementing numbers on re-forks.

### SwiftData gotchas
- `Message.role` is stored as `roleRaw: String` with a computed `MessageRole` property — safer than relying on direct enum support.
- `@Relationship(deleteRule: .cascade)` on `Conversation.messages` with `inverse: \Message.conversation`. Cascade is what cleans up messages when a conversation is deleted.
- Never touch `ModelContext` off the main actor.
- Saves happen **once at end of stream**, not per token. SwiftUI re-renders on property mutation without a save.
- In-memory test stores: `ModelConfiguration(isStoredInMemoryOnly: true)`.

## TDD conventions — follow these strictly

1. **Pure logic is tested first.** Add the failing test, then the minimal impl, then refactor.
2. **SwiftUI views are not unit-tested.** Manual E2E only.
3. **Tests must be deterministic.** Inject clocks. Inject clients. No real network. No real time for logical state.
4. **Fake, don't mock.** `FakeMLXClient` (in `ChatViewModelTests.swift`) is a scripted state machine. `MockURLProtocol` (in `LocalMLXTests/MockURLProtocol.swift`) serves canned `URLSession` responses. No runtime assertions inside test doubles.
5. **Fixtures live in `LocalMLXTests/Fixtures/`** and are loaded via `TestBundle.loadFixture`.
6. **One behavior per test.** Test names are `test_<feature>_<scenario>`. Verbose is fine.
7. **Don't test SwiftData relationship implementation details.** Test observable behavior (cascade delete works, ordering is correct) not internal storage.

## Known risks and likely first-build failure points

In rough order of how likely I think each is to bite you:

1. **Swift 5.10 strict-concurrency warnings upgraded to errors.** Most likely on `LiveMLXClient` conforming to `MLXClientProtocol: Sendable`, `MLXClientEnvironmentKey.LiveHolder: @unchecked Sendable`, and `Task { @MainActor [weak self] in ... }` inside `ChatViewModel`. Fix: add explicit `@unchecked Sendable` where Swift can't prove it, or wrap in `@MainActor`-isolated helpers.

2. **`.searchable(placement: .sidebar)`** inside a `NavigationSplitView` sidebar column. Documented to work on macOS 14 but historically finicky. If it flickers or doesn't appear, move it to a toolbar placement.

3. **`@MainActor private static let sharedModelsVM`** in `LocalMLXApp`. Static lazy init on `@MainActor` should be fine but may need to move into a `.task` if the compiler complains.

4. **`#Predicate { $0.id == id }`** in `SingleChatWindow`. SwiftData UUID predicates with captured locals work in macOS 14, but error messages are opaque when they don't. Fallback: fetch all and filter in Swift.

5. **`SplashCodeSyntaxHighlighter`** — Splash's `OutputFormat` / `OutputBuilder` protocols have little documentation. If it doesn't compile, the easy fix is to have `highlightCode` always return `Text(content)` and drop the Splash dependency.

6. **`tools/generate-icon.swift`** — I couldn't run this. The AppKit SF Symbol rendering path has a weird dual-draw hack; if it produces a blank icon, the fallback `glyph = "✦"` path at the bottom still draws a recognizable mark.

7. **`.fileExporter(document:)`** with `MarkdownDocument`. `FileDocument.init(configuration:)` throws unconditionally because we only write. Export should work; reading will fail — which is fine because we never read.

8. **Timing-sensitive tests.** `test_stop_cancelsInFlightStream_keepsPartialContent` and `test_send_computesTokensPerSecondWhenElapsedIsMeasurable` use real sleep. On a loaded CI machine they could flake. Bump the delays if they're unreliable.

  -project LocalMLX.xcodeproj -scheme LocalMLX \

  -project LocalMLX.xcodeproj -scheme LocalMLX \

  -project LocalMLX.xcodeproj -scheme LocalMLX \
  -destination 'platform=macOS' \

# curl sanity check
